# Networking, routing and synchronization — NET

The same event can cross direct or optional indirect routes. Paths supply bytes and health metrics; they never mint authority. Details in [PROTOCOL.md](../protocol/PROTOCOL.md).

**BLE profile status:** `lattice-ble-exp0` is an experimental candidate, not an interoperable release ([`10-ble.md`](../../protocol/specs/10-ble.md), [ADR-005](../decisions/ADR-005-ble-exp0-profile.md), [candidate byte vectors](../../protocol/vectors/ble-exp0.json)). Android reads and requires the exact three-byte `000000` capabilities value before notification/session setup; fixture-backed JVM tests cover advertisement, capability, control, frame, and GATT UUID semantics, while Rust tests verify identity and deterministic Noise vectors. No physical Android device, independent implementation, or interoperability acceptance is claimed.

**Boundary conditions:** all relevant phones suspended means no local courier work; Internet relay can log size/timing/IP and retain ciphertext; Nostr events are not a file store; BLE is not a continuous audio medium. [Bitchat's whitepaper](https://github.com/permissionlesstech/bitchat/blob/main/WHITEPAPER.md) is implementation precedent, while [DTN RFC 4838](https://www.rfc-editor.org/rfc/rfc4838) frames opportunistic storage.

## Path lifecycle and separation

`discovered → link opening → authenticated → active → degraded → closed` is per path, not per person. One pair may have BLE and LAN simultaneously. Path metrics include last successful receive, smoothed latency, available payload size, queue pressure, recent failures and metered/power context. An adapter gives capabilities and opaque send receipts; the router chooses where to send; the core validates received events. GATT enqueue, WebSocket `OK`, and courier deposit each have different receipt scopes and must not be translated into destination delivery.

The experimental [`lattice-ble-exp0` profile](../../protocol/specs/10-ble.md) specifies candidate GATT UUIDs, rotating-token discovery, a first-contact identity-bound Noise session, MTU floor, 24-byte frame header, four-frame credit window, 110 KiB envelope cap, and connection-local retry ownership. Android now requires exact capabilities negotiation before session setup and has fixture-backed JVM conformance coverage; Rust verifies candidate identity and Noise vectors. These tests do not establish measured interoperability. Physical NET-001/002 acceptance remains open; BLE is low-volume, not a bandwidth or background-scanning guarantee. A faster path must be authenticated and preserve event identity.

The shared protocol crate defines a bounded, canonical version-1 offer for LAN, Wi-Fi Aware and Wi-Fi Direct/P2P frame limits. `lattice-node::sync::negotiate_authenticated_path_upgrades_once` exchanges offers over a separately domain-bound Noise XX session, verifies each peer against the caller's pinned identity, applies the caller's peer-authorization callback before offers, and intersects limits using the smaller frame size for each common path. This reports supported sizes only; it does not prove reachability or open a path. No platform path adapters are wired to the negotiation yet, so NET-006 remains incomplete.

`lattice-transport::TcpPeerAdapter` provides bounded 4-byte big-endian framing over a connected TCP stream; `connect` opens an outbound stream and `TcpPeerListener` binds a caller-selected endpoint and accepts inbound streams with the same envelope cap. The adapter checks lengths before allocation, treats cancellation during an incomplete send as a fault, and reports only local OS queue acceptance. Neither API authenticates peers, discovers LAN devices, nor provides retry/delivery semantics. Together with the authenticated offer exchange, these are transport/protocol primitives, not evidence that a platform LAN or Wi-Fi path is discoverable or active.

Separately, Android's Identity panel exposes `MobileClient::exchange_direct_messages_once`, which uses caller-selected TCP connect/listen endpoints and the same transcript-bound pinned Noise direct-message protocol as Desktop. Both peers run one connect and one accept concurrently; the exact identity pin is checked before socket setup, and authenticated ingress receives at most one due opaque DM packet in each direction. This is an explicit TCP LAN route for direct messages, not discovery, Wi-Fi Aware/Direct, negotiated path-upgrade capability, Router fallback, or a general attachment adapter. Physical Android routing and Android↔Desktop process interoperability remain unverified.
`lattice-node::sync::send_authenticated_attachment_once` and `receive_authenticated_attachment_once` transfer a caller-authorized manifest over a separate pinned Noise XX domain. The receiver checks peer authorization and explicit consent before accepting, sends a bounded missing-chunk bitmap for resumption, and ACKs only after chunk and whole-file integrity verification. The caller owns the signed-manifest authorization and private staging store; every requested chunk must fit the active adapter frame. Desktop and Android wire these APIs to pinned TCP send/receive, bounded private staging, explicit consent and verified export. Android exposes manual SAF import/export, selects a transfer using a signed event ID and caller-entered endpoint, and resumes the same transfer's missing chunks over TCP; it does not use BLE or relay for attachment bytes or integrate Router path negotiation. Physical Android transfer and cross-client process interoperability remain unverified.
`lattice-router` supplies a deterministic bounded planner; it keeps Presence off persistent Courier/InternetRelay routes and Voice on one direct realtime-IP route. `lattice-node::sync` retains the v1 `execute_authenticated_sync_once` / `serve_authenticated_sync_request_once` APIs and adds `execute_authenticated_sync_v2_once` / `serve_authenticated_sync_v2_once`. V2 uses a distinct Noise XX prologue, transcript-bound Ed25519 proof domain, and `LSYN` wire version 2; the existing v1 wire encoding is unchanged. Both paths bind peers to caller-supplied `PinnedIdentity` values and require exact peer/scope authorization before sending or loading scoped sync data.
`lattice-router::assess_paths` returns one ordered per-candidate eligibility result with its first exclusion reason for the local routing request (for example, caller-reported unreachability, missing RTT under an RTT-constrained policy, or queue/loss limits). It evaluates the supplied snapshot; it does not persist adapter errors or infer global peer presence. `lattice-node::path_health::PathHealthTracker` retains at most 64 explicitly registered paths, adapter lifecycle, each latest typed send result, last completed receive time, and consecutive failed sends. It rejects out-of-order completions and never turns an exact-hop receipt into delivery. Neither tracker persists observations; platform callers must feed actual adapter outcomes.
V2 exchanges one bounded summary from each peer; the initiator compares them with `lattice-sync::plan_sync` and requests exact dependencies before sequence gaps from the responder, with at most 128 targets in one batch. The caller provides `SyncSummarySource` and `SyncEventSource`; the responder invokes them only after peer authentication and scope authorization. `StoreSyncEventSource` serves only committed, signature-verified records from one caller-selected Space/group generation; `StoreSyncSummarySource` builds a bounded summary for that selected generation. Peers derive the opaque scope with `space_generation_scope_id(space_id, group_reference)`. CLI `sync fetch-once` uses committed local history plus pending dependencies to request one bounded repair batch; optional `--event-id` replaces pending dependency targets with that exact event. `sync serve-once` returns only targets in the authenticated summary-derived plan. The CLI uses v2 over direct TCP, but does not integrate adapter selection, the outbox, or relay sync-control. Receipts remain exact-hop only.

`StoreSyncSummarySource` builds one selected Space-generation summary from signed local event records and bounded pending dependency metadata. It scans at most 16,384 committed records and 16 MiB of signed bytes, and refuses summaries exceeding the sync limits rather than truncating them into a false completeness claim. Pending events contribute only their missing dependency IDs; they are not reported as accepted history.
On v2, the responder rejects any request target absent from the summary-derived plan before accessing the event source.

## Routing classes and queues

| Class | Priority/persistence | Routing behavior |
| --- | --- | --- |
| Security dependencies | Highest, bounded | MLS proposal/Commit/Welcome, membership and required policy before dependent data. |
| Interactive text | High, durable sender outbox | Direct path first, eligible courier/relay under policy. |
| Deferred history | Medium, resumable | Anti-entropy in batches, prefer fast path. |
| Files | Low/bulk, chunk-resumable | Direct IP preferred, explicit BLE small-file policy. |
| Presence/typing | Volatile | Never persistent courier or backfilled after expiry. |
| Voice media | Real-time only | WebRTC IP path; never stored/flooded as event traffic. |

Sender outbox persists locally and retries on contact discovery with exponential/jittered backoff; a new viable path may wake it early. The storage crate provides schema-v11 SQLite retention for opaque courier bytes, disabled by default, with persisted quotas, expiry, deduplication, FIFO eviction, and transactional copy-budget consumption. CLI and desktop nodes support explicitly initiated pinned TCP courier transfer; each session retains at most one validated envelope. In courier wire v2, the receiver sends an ACCEPT retention ACK only after durable local queue insertion (or confirmation that an identical envelope is already retained); the authenticated response contains the six-byte protocol header followed by the exact 32-byte forwarded protocol envelope ID. It confirms this peer's local ciphertext retention only—not onward forwarding or destination delivery. The sender consumes its source copy only after validating the pinned peer session and matching envelope ID in that ACK; disconnect, timeout, malformed or mismatched ACK, and rejection preserve the source for retry. Exact duplicate retries are idempotently ACKed without adding another queue row. Desktop forwarding is manual and exact-pin authenticated. Its user-triggered mDNS scan exposes only unauthenticated endpoint candidates; it does not connect or authenticate peers. Automatic contact selection, background retry, and resumable courier…

## Synchronization details

NET-005 requires scoped summary exchange and bounded repair. The direct v2 APIs now exchange one summary from each authenticated, authorized peer and use `plan_sync` for a single exact dependency/range request batch; the summaries preserve per-author contiguous positions, sparse event IDs, explicit gaps, and missing dependency IDs. A request contains at most 128 targets, and both summaries and event replies must fit one Noise/adapter frame. Summary count bounds follow `lattice-sync` limits; a summary that exceeds the negotiated frame is rejected rather than paginated.
The existing v1 APIs continue to accept caller-supplied summaries and retain their original v1 frames. V2 validates returned event bytes through the caller's validator before inner-ID deduplication; unavailable, rejected, or frame-omitted targets remain explicit unresolved requests. Transport receipts report only exact-hop acceptance, not destination delivery.
This is partial NET-005 support, not proof of full partition convergence: each v2 session performs one summary exchange and one initiator-to-responder repair batch, does not refresh summaries after returned events, and does not continue with another range batch after resolving dependencies. The responder's own missing events require a separate session in the reverse direction; callers must open another session to continue repair. A signed parent dependency is requested before sequence ranges, so a control-Commit dependency blocks later ciphertext until the requester refreshes its summary. The transport does not inspect opaque MLS bodies to infer Commit type or apply events. Core coverage supplies the authenticated boundary: a real out-of-order membership test retains epoch-two ciphertext pending behind missing control and policy-parent events, accepts it after the Commit transition, then accepts the retried ciphertext. Pending rows are not automatically retried; callers must resubmit them once prerequisites are committed. CLI fetch-once still does not refresh summaries.

## Remote bridge and privacy

The candidate [`13-relay.md`](../../protocol/specs/13-relay.md) defines an opaque Nostr envelope event, relay-only outer key, opaque mailbox tag, expiry, bounds, and best-effort backfill under [ADR-003](../decisions/ADR-003-nostr-envelope-relay-profile.md). The Core authorizes a generation-scoped mailbox token only after MLS admission and protects it locally; an MLS-protected kind-11 control event distributes it to admitted members. `lattice-node::relay::publish_outbox_entry_to_two_relays` wraps and publishes one selected durable outbox envelope concurrently to two distinct configured relays, recording only `Forwarded` after any positive relay acceptance; `retrieve_mailbox_from_two_relays` bounds and deduplicates returned messages, and the CLI passes retrieved inner event bytes through normal Core ingress. `relay mailbox-publish` queues the control event but performs no network request; `relay round` uses the first two configured relay URLs. Offline unit tests cover wrapping, deduplication, integrity conflicts and per-relay acceptance/failure mapping. No independent live relay services or cross-client relay acceptance were exercised; relays may disagree on acceptance/retention. Encryption does not hide client IP, timing, size, or relay-visible tags.
